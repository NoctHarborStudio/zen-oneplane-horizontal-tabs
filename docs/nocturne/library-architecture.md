# Nocturne Library — implementation RFC
Status: L0–L6 functional preview, L7 automated stabilization implemented; native Zen/Sine acceptance remains pending.
Baseline: 050f6f418ef7768f6affef843c7b8137a9ea8e65. Zen source reference: zen-browser/desktop@37e772656a612f19732506b38a4f985bb3cf95a6; verify exact installed Zen 1.24.2b APIs before enabling.

## Product contract
One centered, translucent browser-chrome Library. Five sections: All Downloads, Documents | History | Pictures, Recently Closed. History is the central primary action; title of the active section centered independently of left/right controls. Ctrl+H opens History every time (from another section switches to History; from History toggles closed); Ctrl+J and the Downloads Dock All Downloads action open Downloads once the service is ready. Recent download card stays anchored and separate; no second full downloads view after cutover. Escape priority: native child menu/confirmation > Library > underlying surface. No file scans merely on opening History. No legacy Refined dependency.

## Source findings
- Existing manifest is Nocturne, with independent Sine entrypoints and deterministic layout/CSS source-fragment build (scripts/build-plan.json). Do not rely on execution order or put Library inside installTabStrip.
- Home has a per-window leased registry, owns covered tabpanels/inert and its URL bar search choreography. Hub owns a top-layer popover, hold and cancelable motion. Center Motion animates the tab strip, not dialogs. None is currently a general modal coordinator.
- downloads-indicator.uc.mjs owns native Downloads.getList(PUBLIC/PRIVATE), a generation-guarded view, history map, recent/full row cache, native file drag, clear-record actions and host holds. Its public API exposes summary/setHost/dispose, not a full records service.
- Zen zen-sets.js maps key_gotoHistory, Browser:ShowAllHistory and Tools:Downloads to ZenLibrary.toggle in capture. Verify command interception ordering (including menu and accelerator) on target; do not globally replace ZenLibrary.toggle or disable Zen Library pref. Fall back to native if not ready/supported, preserve spaces/boosts/native menu access. No synthetic double event.
- Zen history uses PlacesQuery.getHistory/searchHistory and observeHistory, PlacesUtils.history; native query can group or return URL-level records. Do not pretend a row is a distinct visit if underlying identity is URL-level. Deletion semantics explicit; time-range deletion via supported Places API. Native closed tabs via SessionStore.getClosedTabData({sourceWindow: window}), closedId and undoCloseById; observer sessionstore-closed-objects-changed. Closed tabs are not Hub Trash.
- Zen Downloads uses DownloadsCommon.getData(window,true), including historical records; compare against current Downloads.getList before selecting canonical source. Do not quietly broaden existing clear-record semantics.
- Zen Media opt-in false, default folders downloads,documents,pictures; native scanner @mozilla.org/zen/library-files;1 with depth 2, 60 dirs, 300 results; classification helpers in ZenLibraryUtils.sys.mjs. Use feature detection; fallback downloaded files only.

## Dependency direction / ownership
Native adapters -> per-window services -> Library controller -> DOM view. View dispatches intent; never performs privileged I/O. Shared Downloads service owns one native subscription per privacy scope/window (or shared scope only if audited), immutable normalized records, opaque native action handles, subscribe/getSnapshot/action/dispose. Dock and Library consume it; no second observer or polling. Preserve active progress, completion flight, native drag payload synchronously on trusted dragstart, existing cancel/retry/open/reveal behavior. Keep the source DOM stable during native drag. Compare historical DownloadsCommon coverage, then merge/deduplicate only if needed with explicit identity and privacy rules. Service lifetime independent of indicator preference; view lifetime lease-based. Remove legacy full Dock only after parity tests. Native operations revalidate identity/exists and eligibility at action time.

Per-window overlay coordinator: register exclusive interactive surfaces, acquire/release a token, request close with reason, maintain focus restoration and source-aware toolbar hold. No global CSS inert toggles that undo another owner's changes. Library may overlay idle Home; never close Home's selected placeholder just to open History. Search must hand off via Home/native cancellation API before Library acquires focus. Hub/recent/full Downloads close through their public contracts; opening Hub or native search releases Library. During native drag, startup/close animation, customization, unsupported popup/fullscreen, or transition conflict use explicit defer/decline policy (native fallback only when safe). Workspace/selected-tab changes close Library except explicitly tagged background operations. Real top-level shutdown always immediate. Escape dispatched to highest active owner; existing capture listeners must cooperate, not depend on registration order.

## State and request flow
Pure reducer src/algorithms/library-state.mjs defines closed/opening/open/switching/closing, active section, query/filter/sort, motion epoch and query epoch. UI state is window-local; each opening resets History query/filters unless explicitly opened to Downloads. Section changes clear selection/query, maintain panel geometry and allocate one new request epoch. Reducer never touches DOM or native APIs. Controller validates epoch after every await; old results cannot replace current section. Abort/close cancels observers, tasks, previews and animations; unsupported native operations fail locally. View renders loading/empty/error/retry distinctly. Use stable record keys and bounded list pages, not full DOM replacement every progress tick. One search debounce (~160ms), immediate Enter/clear, native query pagination (initial 100 or smaller), idle visible favicon/thumbnail loading, bounded cache; no disk cache of history/query. Native notifications coalesced only while relevant view active.

## Layout / design
Single shell in chrome top layer or dedicated browser-chrome overlay root with verified Gecko hit testing; not content script, not per-tab document. Dialog semantics, focus loop, keyboard navigation and accessible close. Center inside measured usable browser client rect, excluding real visible toolbar/bookmarks and sidebar if applicable; do not center on physical screen. CSS grid left and right equal tracks, center History; centered title grid independent of tool width. Suggested width min(960px, available - 40px), height min(740px, available - 40px); compact 12px outer margins, 8px min on small windows, inner list scroll; no 900px breakpoint. At narrow widths secondary pairs stack into two lines or use short labels while preserving all actions. Search and header fixed; inner list scroll. Glass semantic tokens derived from theme, contrast and reduced transparency fallback. One stationary blur backing, not per-row blur; page remains visually behind but blocked from interaction while modal. No full-screen window drag hitbox; browser controls outside remain native where safe. Geometry read only on open/resize/layout event, coalesced via one frame.

## Motion specification
One animation owner and epoch; WAAPI transform/opacity, fixed shell bounds. Open: 260–320ms, scale .97->1, y 8->0, opacity 0->1; backdrop fades 180–220ms. Header/search follow after ~45ms; first visible rows fade/translate 4–6px in capped stagger (max 6–8). Close: 200–240ms reverse from current painted state; disable interaction immediately, release hold and restore focus once after completion. Reopen during closing samples current visual state rather than flashing; cancellation settles cleanly. Section switch: header/nav stable, active underline translate/scale measured once, old content fades/shifts 6px out (~90ms), new content enters (~160ms), keep layout width/height stable. Latest selection wins; loading skeleton appears only after short delay (~120ms), no blank frame. Search updates keyed rows without full section transition; avoid animating each result on typing. Downloads progress updates independently; image decode lazy. Reduced motion / duration zero: immediate state change. Resize does not replay entrance; cancel/rebase bounded motion. Do not invoke Center Assembly on Library open. Respect window shutdown, focus and animation pref; no perpetual RAF.

## Data / actions
History: URL/title/domain, native time/group/key/favicon, search, dates/sort, open foreground or background with native container rules, copy URL, explicit remove page history vs clear time range. Do not use privileged open for arbitrary javascript/data/file URLs; validate and native link helpers. No forget-site-data action in first release (different scope).
Recently Closed: closedId, current window scope, revalidate native id before restore/forget, native restore preserves state; never substitute URL navigation. Privacy and unsupported context -> native fallback or disabled section.
Downloads: existing full/recent actions and native drag parity; explicit Clear completed records, never deletes files/cancels active/blocked/partial. Native launch/reveal only with validation.
Documents/Pictures: downloaded files from shared service by verified file type and existence; optional explicit folder opt-in and folder list. Scanner on entry or refresh, not startup. Dedup normalized native paths (OS-aware); provenance downloaded/local; thumbnails only approved image types in privileged UI with safe handling, no active SVG/HTML execution, no remote fetch; bounded cache and release on close; file missing/permission/error states. Screenshots filter is heuristic by name/location, not browser capture history. Local delete not in first release. Do not expose personal file paths/URLs in telemetry.
Private windows: default native History fallback, no public history/media scan; private downloads isolated and only native closed data for that window if verified. No disk writes of library data; only UI settings/opt-in folders in prefs, never queries or history.

## A7 / NC4-022a — local image decode and native scan budget (source audit, no runtime changes)

**Pinned review:** Nocturne preview.130 at `7d993db91e3bc0c63510206daab2cfd64ce5fc4f`; Zen Browser desktop tag `1.24.2b`, `src/zen/library/nsIZenLibraryFiles.idl`, `nsZenLibraryFiles.cpp`, `sections/ZenLibraryMediaSection.mjs` and `ZenLibraryUtils.sys.mjs`. Source statements below are **not** a measured Zen memory leak, a native crash or a new validation PASS.

**Existing ownership and supported behavior.** `src/services/library-services-runtime.js.part` starts a private-window-excluded, pref-gated scan through Zen's existing native `nsIZenLibraryFiles.scanMedia` with maxDepth=2, maxFolders=60, maxItems=300. Cloud placeholders recorded by Zen are filtered before a Nocturne media row is committed. The service serializes scans within its window, revokes old sessions on pref/folder changes, uses opaque file handles and checks a file/cloud placeholder again before an Open/Reveal action. `src/library/data.mjs` renders only the current page (default 50, UI maximum 500), and `src/library/controller.js.part` sets `loading="lazy"` and `decoding="async"` for its 32px icon/thumbnail. Closing/unloading clears the session and DOM rows. None of these contracts guarantees a decoded-memory ceiling.

**S/P1 — image decoding is not bounded by input size.** The predicate `safeRaster(name,size)` only accepts certain extensions and compressed file size 0 < bytes <= 2,097,152. `describe` then creates a direct `file:` URI, and `updateFileRow` assigns it to an HTML `img` element; CSS width/height 32px only sizes the display. Zen's native scanner `nsIZenMediaFile` exposes path/root/lastModified/size/cloudPlaceholder and **no pixel dimensions**. The source predicate accepts an illustrative `16384x16384` PNG of 150,000 compressed bytes; a full RGBA surface at that resolution alone would be 1 GiB. This is a theoretical decoded surface bound, not an observed allocation; browser optimizations and lazy rendering can lower real use. `img.loading` and `img.decoding` do not certify a pixel/frame budget. GIF and other animated/large raster formats need special care.

**S/P1 — native scan's returned-item limit is not an enumeration-memory limit.** Pinned Zen `nsZenLibraryFiles.cpp` appends every matching `FoundFile` to `aFound`, sorts the full vector after walking the directories, then truncates to `aMaxItems` (300). Nocturne cannot enforce an internal top-K bound by lowering `maxItems`; a very large directory can cause significant native temporary allocation/work despite only 300 returned entries. This is an upstream native-scanner limitation shared by the Zen Library; the exact peak on real user folders has not been measured.

**R/P1 — cloud and link TOCTOU.** `cloudPlaceholder` is a scan-time snapshot. A file can change to an online-only placeholder before `file:` image decode; unlike Open/Reveal, image loading has no fresh `isCloudPlaceholder` check. The native scanner excludes symlink **directories** but does not explicitly exclude symlink files; a symlink can point outside the selected root. The practical filesystem/OS behavior requires confirmation, and neither issue establishes remote upload or external access by itself. Windows uses native offline/recall attributes; on non-Windows `IsPathCloudPlaceholder` currently returns false.

**R/P2 — concurrency.** The scan barrier and owner are window-local. Independent normal windows may run scans of the same roots concurrently, possibly multiplying native temporary work; no measured multiwindow peak exists. Avoid duplicating a process-wide native owner solely as a speculative optimization.

**Comparison with stock Zen.** Zen 1.24.2b `ZenLibraryMediaSection.mjs` uses the same scanner limits (depth 2, 60 folders, 300 items) and assigns raw `file:` URLs for eligible images, guarded by an IntersectionObserver around visible cards. Therefore identical limits/native contracts are deliberate baseline behavior, **not** proof of bounded decoded pixels or scanner memory.

**Exit decision and remediation order.** Do **not** silently remove picture previews or claim safe bounded decoding in preview.130; current UI is user-visible and has no confirmed correct drop-in dimension/cancellation API. First validate native memory/scan/decoder behavior on a disposable target profile and decide the accepted fallback. Preferred structural solution is a small native thumbnail/metadata capability (or verified equivalent) that rejects oversized dimensions/frames before full decode, returns only bounded small surfaces, limits concurrent work and revokes old results. In the native scanner, use bounded top-K retention instead of collecting every `FoundFile` before sorting; retain newest-first semantics and a hard folder budget. Within Nocturne, one existing session should remain the authority for thumbnails and should defer `file:` decode to visible rows, revalidate cloud state at activation and release results on stop. A generic IntersectionObserver alone does not enforce pixel/decode limits. A temporary icon-only fallback is technically safer but changes accepted imagery and needs a separate UX decision. Verify failure, reload, private-window, multiwindow, symlink/cloud and release-gate behavior before claiming completion.

**Status:** NC4-022a source audit COMPLETE; NC4-022 decoded-memory/native-scan remediation and native Zen profiling OPEN. No release version, runtime, prefs, generated sources or Sine installation changed.

## A7 / NC4-022-S1 — media preference observer-order repair (preview.131)

**Source-extracted reproduction on preview.130:** `src/library/controller.js.part:onMediaPref()` synchronously called `renderBody() -> createLibraryData.start() -> openMedia() -> media.open()`. `src/services/library-services-runtime.js.part:onMediaScopeChange()` independently invoked `media.invalidate()` when the same pref changed. **Minimal repair:** The existing controller retains its own pref observer and schedules one coalesced `win.queueMicrotask` reload. The queued callback checks dead/active/section/closing state again; native file drag keeps the existing deferred-close contract. A bounded existing `library.media.scope.reload` trace records only the section, never filenames/paths. No independent timer, extra observer, new service, UI feature or native API. The media service's generation and per-session owner remain unchanged.

**Verification:** The two source-extracted regression cases exercise both notification orders, repeated notifications in one turn, disposal before the queued refresh and active file drag; prior controller-first order fails against preview.130. Exact Sine/Zen runtime ordering must still be verified in a disposable profile; source callback tests are not native acceptance.

**Non-goals:** A microtask does not cap image pixel decode or Zen's native C++ pre-truncation accumulation. NC4-022a source findings and NC4-022 decoded-memory/native-scanner remediation remain OPEN; do not close those gates or modify thumbnail UX as a side effect of this lifecycle fix.

## A7 / NC4-076 — Downloads bulk-clear skipped-state feedback (preview.133)

**Confirmed source fixture (preview.132):** the existing `createDownloadsService.clearCompleted()` snapshots two native records initially `clearable`, then the first `DownloadList.remove` updates the second to `hasPartialData=true`. `actionNative(second,"remove")` correctly rejects this now-ineligible entry and leaves the native record untouched, but the returned summary was `{removed:1,failed:0}`, indistinguishable from a fully successful one-record batch. The Library used only `failed` to choose its user-visible notice. This is incorrect *reporting*, not unsafe native removal.

**Minimal correction:** keep the original serial loop and native `actionNative` guard. Count each initial eligible target as `requested`, increment `removed` only when native reports success, `skipped` when it returns false, and `failed` when it throws. The invariant is `requested===removed+skipped+failed`. The existing Library confirms before clearing and now reports partial completion for either skipped or failed entries. A single content-free `library.downloads.clear.result` trace contains only these four counts. Do not change native DownloadList.remove, eligibility semantics, add retries, touch disk files or affect the Dock's independent interaction path.

**Source tests:** one existing result test updated and three new test fixtures exercise mid-batch state invalidation, native removal throw, and visible Library status. No native user-profile or real Zen Downloads run was performed. The scope remains per existing Downloads service and Library action, not a cross-window atomic clear. Native Zen acceptance and verification of actual DownloadList event ordering remain OPEN.

## A7 / NC4-090 — one Downloads bulk-clear owner across Dock and Library (preview.134)

**Source reproduction at preview.133:** `downloads-indicator.uc.mjs:clearHistory()` manually iterated its `history` Map, calling `list.remove(d)`, while `src/library/controller.js.part:clearDownloads()` separately called `downloads.clearCompleted()`. Both used the same native Downloads service, but their orchestration was independent. With one initially clearable record and a deferred native `DownloadList.remove`, a source-extracted Dock handler and real `createDownloadsService` called native `remove` **twice before the first call completed**. This confirms a same-window concurrency bug, not native data loss.

**Existing-owner correction:** Dock now invokes `source.clearCompleted(continueIf)` instead of its old iteration. The existing DownloadsService is the sole bulk loop within the window; concurrent calls return `null` (busy), not a borrowed result implying the second confirmation succeeded. The existing `actionNative("remove")` keeps a short in-flight set keyed by native Download identity so a concurrent Library row Remove cannot issue a second `remove` during the first Promise. Eligibility is checked again before each native operation; counters retain `requested/removed/skipped/failed`. `continueIf` carries Dock's pre-existing `epoch`/teardown guard; after a window reload, no further native removes begin from the old Dock. The Library retains its current confirmation and displays an explicit busy notice. Dock retains its existing confirmation controls and partial-result notice. No new service, UI surface, list owner, observer, timer, native API or file-delete path.

**Cancellation/identity boundaries:** An already issued native removal is awaited and cannot be safely undone, as in the old implementation. Stale-generation checks stop *subsequent* items; the active Promise's completion can still race teardown. Per-window operation arbitration does not claim process-wide locking: two browser windows have distinct service instances and can still act on the same native DownloadList. Gecko DownloadList event timing and shared list across windows require native acceptance. No personal paths or file names are logged; the Dock's existing sampled diagnostic event records aggregate counts.

**Source fixture tests:** shared Dock/Library overlap, duplicate per-row removal while a bulk operation is awaiting native completion, stale Dock generation after the first item, Dock UI handoff after teardown and Library busy reporting are exercised against production code. Source/CI and native runtime are separately gated.

## A7 / NC4-090-R2 — pending native removals belong to disposal (preview.135)

Independent source reproduction on preview.134 found that `createDownloadsService.dispose` waited for an in-progress native `addView` but not for a pending `DownloadList.remove`. The previous view could be detached and the replacement lease granted before an already issued removal completed; a source fixture observed two native remove calls for the same Download simultaneously across reload.
