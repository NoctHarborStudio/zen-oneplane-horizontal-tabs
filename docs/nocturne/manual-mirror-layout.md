# Manual Mirror Layout — A4.5 / ML0–ML7

Status: **user-approved visual interaction concept; PLANNED, not implemented**. No production changes are authorized by this document alone. Relevant scope: horizontal OnePlane tab strip within **one real Zen Workspace**, not two Workspaces, no virtual native tab collections. Keep the existing automatic adaptive layout selectable and behaviorally unchanged. UI prototype v3 was accepted conceptually; HTML mock is not native Zen evidence.

## Approved product contract

1. Two modes: **Automatic** (existing symmetric adaptive distribution) and **Manual** (independent left/right sides around the fixed central Home). Manual may be selected by the user; do not silently switch mode or assign sides based on available space.
2. Logical sequence on **each side is center → outward**. In Manual, no tab crosses Home because of tab count, window resize, Home title width, second-row capacity, icon loading, or other automatic repartition. A deliberate user drag or explicit user command may change the side.
3. Visual **right** sequence is left-to-right: nearest Home is 1, then 2, …, and finally its own `+` at the outer **right** end. Visual **left** sequence is the mirror: nearest Home is 1, then 2 farther left, and finally its own `+` at the outer **left** end. Reverse display **within each left-side row**, not the underlying native tab order.
4. The `+` is a real action to open one native tab on its side, **not a permanently fixed first-row decoration**. Reserve a slot for it in the same occupancy/overflow algorithm as tabs, so when its side extends to the lower row, `+` must move to the **outermost end of the lower row**. After creating a tab, that tab occupies the prior next position and `+` advances to the new end. If the side has no tabs, it has no phantom tabs; its own `+` remains available.
5. Precise approved left example with first-row capacity two: logical left `[1,2,3,4,6,+]` gives **upper visual `[2,1]`** and **lower visual `[+,6,4,3]`**. Matching right example logical `[1,2,3,4,5,+]` gives upper `[1,2]` and lower `[3,4,5,+]`. These examples are **acceptance fixtures**; widths/capacity are measured at runtime and not hardcoded.
6. Per-side independent overflow and slider/scroll; maximum two rows under the currently approved concept. When **both** sides overflow, the second row has separate left/right lane regions centered around the Home axis. When **only one** side overflows, the **whole lower row** may be used by that side with content centered, **without reserving an empty half** for the other side. Logical side ownership never changes when a lower row spans the center.
7. `Ctrl+T` follows the side of the currently active real tab (left→left; right→right). Opening a link in a new tab, including Ctrl+Click or an external application, follows the side of the current active tab as agreed. Clicking a specific side's `+` overrides this and creates there. Preserve native tab creation and selection semantics, including single native mutation; do not implement a second browser/new-tab service. An optional explicit-side hotkey is deferred.
8. User can drag tabs across Home to deliberately change side, and reorder within a side; a native **Split View group moves as one indivisible unit** across sides. Never split or recreate Zen groups to fit a visual partition. Native Workspace/tab/group identity, SessionStore, pinned/Essentials/folders remain Zen-owned.
9. **Initial Manual enable:** preserve the current visually painted left/right membership rather than rebalancing. **Switch Manual→Automatic→Manual:** remember the manual assignment and restore it; Automatic must continue to use the existing balancing algorithm. **Restart/workspace switch:** side assignments must survive, without duplicating tab/session state, assuming a valid native identity is restored. No hidden side-specific browser instances or fake Workspaces.
10. Keep current Home geometry, native toolbar/URLbar, bookmarks/contour, hover, overflow and visual design unless this contract explicitly changes them. The approved example is a conceptual HTML mock, not a requirement to copy its colors, text or artificial numbering.

## Ownership and implementation constraints

- Zen is authoritative for native visible tab identity, native order, Workspace and Split View. Layout remains the **sole tab projection/geometry owner**. The new persistent user assignment is **only side metadata** plus the UI mode, not URL/history/tab copies. Resolve actual session-compatible tab metadata API at design gate (feature detection, cleanup, native ID scope, private/profile handling); **do not assume that DOM IDs or in-memory objects survive restart**. Reuse existing adapters and an exact tab/session lease, with no new competing native state store.
- Display order is derived from native authoritative ordering filtered by saved side and grouped as indivisible visual units. If native sequencing cannot preserve the approved within-side order across restarts/drag without an extra order key, document and verify the minimum metadata and its update rule before implementing. No speculative native `moveTabToWorkspace` for moves between sides of the same Workspace.
- Extend the existing pure strip partition plan rather than create a second independent `centerToolbar`/native `TabSync` or an unbounded rendering loop. The plan must output per-side `top`/`bottom` slots plus exact `+` placement; include actual collapsed widths, group widths, Home center, compact/adaptive, focused hover, native toolbar controls and lane scroll geometry. Respect A4 center/height/contour dirty-bit/snapshot contract, drag source-node lease, Split native eligibility and A3 CenterMotion topology/handoff.
- Manual side membership can change only on explicit user placement/open intent, verified native creation/move/closure, native Workspace reassignment, or authoritative session restore; never as a side effect of geometry reflow. Make stale async callbacks fail closed and release their own effects/DOM marks.
- Native keyboard focus/order, tab selection/reveal, indicator clipping, tab hover/Bunny insertion, address cascade, Bookmarks, Home, Compact and Motion need the same side/row-aware topology. Prefer exposing a single current projection plan, not scattered `if(manual)` branches.
- Unknown native eligibility (Essentials, global pin, cross-Workspace group, private/synced/Glance, folder) must fall back safely without silently changing native data or wiping saved side metadata. Decide exact role policy from Zen 1.24.2b source and an independent regression matrix before cutover.
- No independent animation clock, global per-frame layout scan, URL/title logging, new Sine entrypoint, or broad native API replacement. Use bounded `__nocturneTrace` reason/count/side/row/transaction diagnostics and existing `nocturne-diagnostics.json` limits. Native/user visual verification required.

## Decisions to settle at ML0 (not grounds to invent runtime behavior now)

- Is mode selection global/profile-wide or scoped to individual Workspace? Side membership is **per tab within its native Workspace** either way; agree UI preference scope before implementing.
- When selected native tab is absent/Home-only or an external new-tab origin is ambiguous, what conservative side should be used?
- What are the approved behaviors for native Essentials/global pinned tabs, native folders, Glance, and Split groups crossing native Workspace boundaries? Reuse native role semantics; do not synthesize split member relocation.
- Which exact Zen/Gecko session metadata/persistence API is available and reliable for restored identities and auto-mode edits to side membership?
- At extreme narrow widths, should the `+` become horizontally scroll-reachable versus a dedicated overlay? Do not silently add a third row or swap to Auto.

**Dependencies/scheduling:** independent design/prototype may proceed in parallel, but production cutover waits for the relevant A4 layout geometry and A5 source drag contracts, plus a stable baseline after A5.7c; A6 keyboard/native open paths must be reviewed. Do not block unrelated existing A5/A6 work or retroactively mark A4/A5 complete. Full native/performance acceptance is included in A8, not assumed by fixture or HTML prototype. Do not enable as the default merely because ML1–ML6 pass.

## ML0 — source architecture review (preview.203, 113f39ea)

Status: **initial owner/algorithm audit recorded; ML0 remains OPEN**. No runtime changes. The accepted ML0–ML7 product contract above is unchanged.

### Existing coupling and required boundary

- `tab-sync.js.part:readStripTopology/syncNow` already owns one native snapshot, one mirror entry per visible tab and one wrapper per native Split group. `stripOrderSnapshot` is a native-derived unit sequence, not the painted order or side assignment. Keep this invariant; never use reparented DOM to infer persistent side except the explicit first-enable capture.
- `toolbar-center.mjs:restingToolbarBudget` calls `islandBoundary` before `planAdaptiveTabRows`; the existing compact planner can skip nearer group slots and select farther ordinary tabs. That is accepted Automatic behavior, not a valid Manual center-out prefix. `reclaimAddressWidth` checks a single `topPlus` and upper slots only. Manual must compare both plus positions, lower lane ownership and row topology as well. Preserve exact Automatic fixtures and its current geometry.
- `strip-order.js.part:applyStripPartition` materializes three lanes and `window-scope.js.part` creates one global plus and one bottom slider; `hover.js.part` and window lifecycle directly reference those instances. Extend the existing renderer and scoped lane/scroll lifecycle, not a second renderer, parallel observer, or separate animation clock. One-side lower expansion is a physical region change, not a logical side change.
- `geometry.js.part:centerToolbar` snapshots order and phase, computes address budget and applies partition in one transaction. Include side/mode revision in stale checks, before/after reparent and focus callbacks. Keep the same geometry/height/contour coordinator. Center Motion capture, selected reveal, indicator clipping (currently suppressed in overflow), and address cascade must enumerate the committed regions/controls; do not add independent geometry owners.
- `strip-drag.js.part:laneDropTarget` currently resolves empty lanes using a balanced boundary; `drag-controller.js.part:moveNativeNextTo` and `tab-adapter.js.part:nativeStripPlacement` confirm native adjacency, not side membership. A move between Manual sides can be a side-only change even when native order is unchanged, and a native relative move may be necessary even if the visual side is unchanged. A target needs explicit logical side, row/region, native anchor and direction, including an empty-side target. Check native ownership, captured generation and actual native result before committing metadata; never call moveTabToWorkspace for a same-Workspace side change. Preserve native source DOM and existing Drag Engine lease. On failure reconcile actual native state, no speculative rollback or successful animation.
- Preview.203 includes Vanishing Home: `vanishing-home.js.part:beginVanishingHome` assumes only upper left/right nodes and a single plus; `vanishingHomeSlots` assumes one continuous sequence. Do not enable this existing path in Manual until an explicit frozen side/seam mapping and two-control geometry are validated. Use the existing compatible drag fallback if eligible; never infer committed side from the animated Home gap.

### Recommended contracts (design, not new runtime services)

1. One immutable native-unit input snapshot (tab or atomic Split wrapper, native identity/order, collapsed width, eligible role). One Layout-owned side policy resolves Manual or Automatic assignment. Manual derives two center-out sequences from native ordering filtered by side; map left visual reversal to native before/after explicitly. No persistent order key unless fixtures prove it necessary.
2. A common pure plan describes logical side, row, visual slot order, physical region and each real plus placement. Automatic retains its current allocation policy through a lossless adapter; Manual fits an ordered prefix per side, sends the remaining suffix including its trailing plus to row two, and treats groups as units. A plus is a control slot, never a native tab. Distinguish physical full-width lower region from logical ownership. At narrow widths keep both controls reachable via existing scroll mechanics; exact extreme-width UX remains an open decision.
3. A single projection commit uses this plan and a generation guard. Consumers receive the committed plan or a captured drag/motion snapshot, not a separately recomputed boundary. Side metadata is written on explicit confirmed placement/open or reconciliation of native restore, never on resize, hover, or animation. No new Sine entrypoint, duplicated tab cache, new geometry loop or separate animation subsystem.
4. New-tab side intent belongs at the existing native command/event boundary. `window-scope.js.part` already invokes `cmd_newNavigatorTab`; existing `TabOpen`, `SSTabRestoring`, `SSTabRestored` and native selection events are the integration candidates. A short-lived explicit plus intent must be scoped to the exact native creation and expire without an extra tab. Do not use selectedTab after selection changed as proof of previous origin; inspect native opener/creation paths and adoption/restore ordering before choosing the final adapter. Unknown origins must use a documented fallback, not a global command wrapper.

### Persistence evidence and unresolved gates

Firefox 160 SessionStore exposes get/set/deleteCustomTabValue; source handles adoptedTab metadata transfer and restores extData. Prefer a namespaced enum side value on each eligible native tab over a profile JSON database, DOM IDs or a second tab-order store. This is a candidate, not a certified Zen contract. Zen 1.24.2b `ZenSessionManager.sys.mjs:#collectUsedTabsFromWindows` selects one tab-data copy by zenSyncId and active/nonblank priority; `#restoreWindowData` reuses sidebar tab data. `ZenWindowSync.sys.mjs` syncs tab open/move and position; no direct custom-tab metadata propagation was found in the inspected event/position paths. A side value on a nonchosen replica could be lost. Verify actual multiwindow synchronization, adoption, undo-close, duplicate, private/unsynced and restart semantics before ML2; no speculative writes to Zen session files or sync internals. Group merge/unsplit conflict policy, role eligibility and ambiguous open origin still need explicit resolution.
