# Manual Mirror Layout — A4.5 / ML0–ML7

Status: **user-approved visual interaction concept; PLANNED, not implemented**. No production changes are authorized by this document alone. Relevant scope: horizontal OnePlane tab strip within **one real Zen Workspace**, not two Workspaces, no virtual native tab collections. Keep the existing automatic adaptive layout selectable and behaviorally unchanged. UI prototype v3 was accepted conceptually; HTML mock is not native Zen evidence.

## Approved product contract

1. Two modes: **Automatic** (existing symmetric adaptive distribution) and **Manual** (independent left/right sides around the fixed central Home). Manual may be selected by the user; do not silently switch mode or assign sides based on available space.
2. Logical sequence on **each side is center → outward**. In Manual, no tab crosses Home because of tab count, window resize, Home title width, second-row capacity, icon loading, or other automatic repartition. A deliberate user drag or explicit user command may change the side.
3. Visual **right** sequence is left-to-right: nearest Home is 1, then 2, …, and finally its own `+` at the outer **right** end. Visual **left** sequence is the mirror: nearest Home is 1, then 2 farther left, and finally its own `+` at the outer **left** end. Reverse display **within each left-side row**, not the underlying native tab order.
4. The `+` is a real action to open one native tab on its side, **not a permanently fixed first-row decoration**. Reserve a slot for it in the same occupancy/overflow algorithm as tabs, so when its side extends to the lower row, `+` must move to the **outermost end of the lower row**. After creating a tab, that tab occupies the prior next position and `+` advances to the new end. If the side has no tabs, it has no phantom tabs; its own `+` remains available.
5. Precise approved left example with first-row capacity two: logical left `[1,2,3,4,6,+]` gives **upper visual `[2,1]`** and **lower visual `[+,6,4,3]`**. Matching right example logical `[1,2,3,4,5,+]` gives upper `[1,2]` and lower `[3,4,5,+]`. These examples are **acceptance fixtures**; widths/capacity are measured at runtime and not hardcoded.
6. Per-side independent overflow and slider/scroll; maximum two rows under the currently approved concept. When **both** sides overflow, the second row has separate left/right lane regions centered around the Home axis. When **only one** side overflows, the **whole lower row** may be used by that side with content centered, **without reserving an empty half** for the other side. Logical side ownership never changes when a lower row spans the center.
7. `Ctrl+T` follows the side of the currently active real tab (left→left; right→right). Opening a link in a new tab, including Ctrl+Click or an external application, follows the side of the current active tab as agreed. Clicking a specific side's `+` overrides this and creates there. Preserve native tab creation and selection semantics, including single native mutation; do not implement a second browser/new-tab service. An optional explicit-side hotkey is deferred.
8. User can drag tabs across Home to deliberately change side, and reorder within a side; a native **Split View group moves as one indivisible unit** across sides. Never split or recreate Zen groups to fit a visual partition. Native Workspace/tab/group identity, SessionStore, pinned/Essentials/folders remain Zen-owned.
9. **Initial Manual enable:** preserve the current visually painted left/right membership rather than rebalancing. **Switch Manual→Automatic→Manual:** remember the manual assignment and restore it; Automatic must continue to use the existing balancing algorithm. **Restart/workspace switch:** side assignments must survive, without duplicating tab/session state, assuming a valid native identity is restored. No hidden side-specific browser instances or fake Workspaces.
10. Keep current Home geometry, native toolbar/URLbar, bookmarks/contour, hover, overflow and visual design unless this contract explicitly changes them. The approved example is a conceptual HTML mock, not a requirement to copy its colors, text or artificial numbering.

## Ownership and implementation constraints

- Zen is authoritative for native visible tab identity, native order, Workspace and Split View. Layout remains the **sole tab projection/geometry owner**. The new persistent user assignment is **only side metadata** plus the UI mode, not URL/history/tab copies. Resolve actual session-compatible tab metadata API at design gate (feature detection, cleanup, native ID scope, private/profile handling); **do not assume that DOM IDs or in-memory objects survive restart**. Reuse existing adapters and an exact tab/session lease, with no new competing native state store.
- Display order is derived from native authoritative ordering filtered by saved side and grouped as indivisible visual units. If native sequencing cannot preserve the approved within-side order across restarts/drag without an extra order key, document and verify the minimum metadata and its update rule before implementing. No speculative native `moveTabToWorkspace` for moves between sides of the same Workspace.
- Extend the existing pure strip partition plan rather than create a second independent `centerToolbar`/native `TabSync` or an unbounded rendering loop. The plan must output per-side `top`/`bottom` slots plus exact `+` placement; include actual collapsed widths, group widths, Home center, compact/adaptive, focused hover, native toolbar controls and lane scroll geometry. Respect A4 center/height/contour dirty-bit/snapshot contract, drag source-node lease, Split native eligibility and A3 CenterMotion topology/handoff.
- Manual side membership can change only on explicit user placement/open intent, verified native creation/move/closure, native Workspace reassignment, or authoritative session restore; never as a side effect of geometry reflow. Make stale async callbacks fail closed and release their own effects/DOM marks.
- Native keyboard focus/order, tab selection/reveal, indicator clipping, tab hover/Bunny insertion, address cascade, Bookmarks, Home, Compact and Motion need the same side/row-aware topology. Prefer exposing a single current projection plan, not scattered `if(manual)` branches.
- Unknown native eligibility (Essentials, global pin, cross-Workspace group, private/synced/Glance, folder) must fall back safely without silently changing native data or wiping saved side metadata. Decide exact role policy from Zen 1.24.2b source and an independent regression matrix before cutover.
- No independent animation clock, global per-frame layout scan, URL/title logging, new Sine entrypoint, or broad native API replacement. Use bounded `__nocturneTrace` reason/count/side/row/transaction diagnostics and existing `nocturne-diagnostics.json` limits. Native/user visual verification required.

## Decisions to settle at ML0 (not grounds to invent runtime behavior now)

- Is mode selection global/profile-wide or scoped to individual Workspace? Side membership is **per tab within its native Workspace** either way; agree UI preference scope before implementing.
- When selected native tab is absent/Home-only or an external new-tab origin is ambiguous, what conservative side should be used?
- What are the approved behaviors for native Essentials/global pinned tabs, native folders, Glance, and Split groups crossing native Workspace boundaries? Reuse native role semantics; do not synthesize split member relocation.
- Which exact Zen/Gecko session metadata/persistence API is available and reliable for restored identities and auto-mode edits to side membership?
- At extreme narrow widths, should the `+` become horizontally scroll-reachable versus a dedicated overlay? Do not silently add a third row or swap to Auto.

**Dependencies/scheduling:** independent design/prototype may proceed in parallel, but production cutover waits for the relevant A4 layout geometry and A5 source drag contracts, plus a stable baseline after A5.7c; A6 keyboard/native open paths must be reviewed. Do not block unrelated existing A5/A6 work or retroactively mark A4/A5 complete. Full native/performance acceptance is included in A8, not assumed by fixture or HTML prototype. Do not enable as the default merely because ML1–ML6 pass.

## ML0 — source architecture review (preview.203, 113f39ea)

Status: **initial owner/algorithm audit recorded; ML0 remains OPEN**. No runtime changes. The accepted ML0–ML7 product contract above is unchanged.

### Existing coupling and required boundary

- `tab-sync.js.part:readStripTopology/syncNow` already owns one native snapshot, one mirror entry per visible tab and one wrapper per native Split group. `stripOrderSnapshot` is a native-derived unit sequence, not the painted order or side assignment. Keep this invariant; never use reparented DOM to infer persistent side except the explicit first-enable capture.
- `toolbar-center.mjs:restingToolbarBudget` calls `islandBoundary` before `planAdaptiveTabRows`; the existing compact planner can skip nearer group slots and select farther ordinary tabs. That is accepted Automatic behavior, not a valid Manual center-out prefix. `reclaimAddressWidth` checks a single `topPlus` and upper slots only. Manual must compare both plus positions, lower lane ownership and row topology as well. Preserve exact Automatic fixtures and its current geometry.
- `strip-order.js.part:applyStripPartition` materializes three lanes and `window-scope.js.part` creates one global plus and one bottom slider; `hover.js.part` and window lifecycle directly reference those instances. Extend the existing renderer and scoped lane/scroll lifecycle, not a second renderer, parallel observer, or separate animation clock. One-side lower expansion is a physical region change, not a logical side change.
- `geometry.js.part:centerToolbar` snapshots order and phase, computes address budget and applies partition in one transaction. Include side/mode revision in stale checks, before/after reparent and focus callbacks. Keep the same geometry/height/contour coordinator. Center Motion capture, selected reveal, indicator clipping (currently suppressed in overflow), and address cascade must enumerate the committed regions/controls; do not add independent geometry owners.
- `strip-drag.js.part:laneDropTarget` currently resolves empty lanes using a balanced boundary; `drag-controller.js.part:moveNativeNextTo` and `tab-adapter.js.part:nativeStripPlacement` confirm native adjacency, not side membership. A move between Manual sides can be a side-only change even when native order is unchanged, and a native relative move may be necessary even if the visual side is unchanged. A target needs explicit logical side, row/region, native anchor and direction, including an empty-side target. Check native ownership, captured generation and actual native result before committing metadata; never call moveTabToWorkspace for a same-Workspace side change. Preserve native source DOM and existing Drag Engine lease. On failure reconcile actual native state, no speculative rollback or successful animation.
- Preview.203 includes Vanishing Home: `vanishing-home.js.part:beginVanishingHome` assumes only upper left/right nodes and a single plus; `vanishingHomeSlots` assumes one continuous sequence. Do not enable this existing path in Manual until an explicit frozen side/seam mapping and two-control geometry are validated. Use the existing compatible drag fallback if eligible; never infer committed side from the animated Home gap.

### Recommended contracts (design, not new runtime services)

1. One immutable native-unit input snapshot (tab or atomic Split wrapper, native identity/order, collapsed width, eligible role). One Layout-owned side policy resolves Manual or Automatic assignment. Manual derives two center-out sequences from native ordering filtered by side; map left visual reversal to native before/after explicitly. No persistent order key unless fixtures prove it necessary.
2. A common pure plan describes logical side, row, visual slot order, physical region and each real plus placement. Automatic retains its current allocation policy through a lossless adapter; Manual fits an ordered prefix per side, sends the remaining suffix including its trailing plus to row two, and treats groups as units. A plus is a control slot, never a native tab. Distinguish physical full-width lower region from logical ownership. At narrow widths keep both controls reachable via existing scroll mechanics; exact extreme-width UX remains an open decision.
3. A single projection commit uses this plan and a generation guard. Consumers receive the committed plan or a captured drag/motion snapshot, not a separately recomputed boundary. Side metadata is written on explicit confirmed placement/open or reconciliation of native restore, never on resize, hover, or animation. No new Sine entrypoint, duplicated tab cache, new geometry loop or separate animation subsystem.
4. New-tab side intent belongs at the existing native command/event boundary. `window-scope.js.part` already invokes `cmd_newNavigatorTab`; existing `TabOpen`, `SSTabRestoring`, `SSTabRestored` and native selection events are the integration candidates. A short-lived explicit plus intent must be scoped to the exact native creation and expire without an extra tab. Do not use selectedTab after selection changed as proof of previous origin; inspect native opener/creation paths and adoption/restore ordering before choosing the final adapter. Unknown origins must use a documented fallback, not a global command wrapper.

### Persistence evidence and unresolved gates

Firefox 160 SessionStore exposes get/set/deleteCustomTabValue; source handles adoptedTab metadata transfer and restores extData. Prefer a namespaced enum side value on each eligible native tab over a profile JSON database, DOM IDs or a second tab-order store. This is a candidate, not a certified Zen contract. Zen 1.24.2b `ZenSessionManager.sys.mjs:#collectUsedTabsFromWindows` selects one tab-data copy by zenSyncId and active/nonblank priority; `#restoreWindowData` reuses sidebar tab data. `ZenWindowSync.sys.mjs` syncs tab open/move and position; no direct custom-tab metadata propagation was found in the inspected event/position paths. A side value on a nonchosen replica could be lost. Verify actual multiwindow synchronization, adoption, undo-close, duplicate, private/unsynced and restart semantics before ML2; no speculative writes to Zen session files or sync internals. Group merge/unsplit conflict policy, role eligibility and ambiguous open origin still need explicit resolution.

### Exit order

- ML0 remaining: exact native open/restore event ordering (including placeholder reuse), persistence/replica proof and eligibility matrix; capture Automatic fixtures and a full reference consumer inventory on fresh HEAD. Resolve user-visible mode scope/default and special-role policy before cutover.
- ML1 first implement and test the pure planner/common plan adapter with production still on the unchanged Automatic path. Include conservation, per-side order, group atomicity, plus uniqueness/reachability, one/both-side overflow, narrow/resize, stable metadata and existing Auto golden fixtures.
- ML2–ML5 migrate actual consumers through that contract incrementally: metadata, native creation, drag target/commit, then geometry/scroll/motion. Do not publish a partially functional Manual switch. Revalidate the parallel Vanishing Home and material/geometry changes before integration.
- ML6–ML7 retain full existing verify/CI plus bounded diagnostics and actual Zen/Sine runtime gates. No source or HTML test constitutes native acceptance.

## ML0-R — independent design challenge (preview.205, f9840366)

**Status: design review recorded; ML0 OPEN.** This refines the ML0 proposal above, not the approved UX or production runtime. Source references rechecked at the pinned HEAD; Zen native evidence from tag 1.24.2b.

### Rejected alternatives and minimal common contract

- Reject a second Manual controller (duplicates ownership) and a universal strip rewrite (large regression surface). Use a narrow common committed projection contract, with the existing Auto planner retained verbatim initially and a pure Manual allocator. Do not force the two policies to share identical allocation or CSS metrics, invent a plugin registry, global event bus, generic transaction framework or second tab model. Generalize consumers only where the actual two-mode requirements justify it.
- Keep separate concepts: native ordered units; logical side/center-out sequence; physical region and visual order; current measured motion pose. The committed plan contains region IDs, ordered unit/control IDs and logical side where meaningful; it is ephemeral, not persistent, not a second DOM index, and not a source of native identity. Geometry metrics belong to the existing pass; motion owns temporary pose. Reuse existing scope and generation guards. Use one plan publication boundary, not several independently updated side/row caches.
- A candidate plan is not a committed plan. `applyStripPartition` can stop after some DOM moves when reentered; `syncNow` currently publishes syncedTopology even though centerToolbar can return false. Before any structural write invalidate consumer admission, precompute node/region references, then validate current owner, mode/assignment revision, exact unit coverage and actual parents/order after writes. Publish only a verified commit. Partial application invalidates motion/drop admission and schedules the existing reconciliation; no DOM/native rollback, spin loop or second renderer. Keep normal Auto behavior and test this invariant separately before Manual cutover.

### Counterexamples that change the original proposal

- **First enable:** Auto compact allocation returns one `lower` array and may skip nearer Split groups to keep farther ordinary tabs above. Painted lower DOM cannot identify the logical side; using current x-position after centering is also wrong. Capture the committed Auto allocator's exact boundary/provenance in the same snapshot (including lower indices), never recompute with newer widths. Preserve assignment, not promise pixel-identical rows when Manual changes overflow policy. If provenance is unavailable, defer enable until a valid resting projection exists; no arbitrary assignment.
- **Order:** filtering native order in forward direction for both sides reverses the existing left visual chain. For native units in left-to-right order, recommended Manual center-out ordering is reverse(filtered-left) and forward(filtered-right); reverse only the rendered left row relative to its center-out sequence. Example native [L3,R1,L2,L1,R2] yields logical left [L1,L2,L3] and right [R1,R2]. Interleaved opposite-side native units must not require globally sorting tabs into two contiguous blocks. A same-side anchor is the relevant neighbor in the filtered native sequence, not global adjacency. Do not add persisted order keys without demonstrated native inability. Auto edits may change native relative order while side assignments remain dormant; saved side membership and frozen historical order are distinct promises. Define new/missing Auto-era assignments at re-enable without overwriting existing ones.
- **Overflow:** a real plus is the trailing control in each side's logical sequence. If all tabs fit above but plus does not, a plus-only lower row is valid under the current contract; if an empty side has no top capacity, its control still needs a reachable lower region. A single lower physical region can span the entire width without changing its logical side. Use prefix fitting, group atomicity, explicit gaps and measured capacities, and test exact threshold oscillation. Any reserved hover/return margin is a pure input, not inferred from transient painted width. Address-width reclamation must preserve the complete structural signature (both plus placements/regions), not just upper slots. Do not require geometry metrics equality when only spare width changes.
- **Drop:** target expresses logical side + insertion gap between same-side units, with row/region as hit-test context, not an authoritative native anchor guessed from the animated DOM. Translate to a verified native anchor/direction at admission, then check the resulting filtered sequence and intended identity/role; do not force a global move solely to satisfy adjacency across opposite-side units. Empty side (including sole source tab) can be a metadata-only commit after native identity validation. Do not reuse the existing cross-window empty-Workspace adoption gate for this case. Separate native placement outcome from side metadata outcome; partial native success is not a confirmed Manual move, no destructive rollback, no automatic retry. The existing gesture lease settles exactly once. For Split merges/unsplits and conflicting member metadata choose explicit verified native-event reconciliation policy before implementation; keep one atomic visual group even if metadata is inconsistent. No per-frame writes.
- **Motion:** current Vanishing Home assumes one plus and ordered x positions from stripNodes; return checks the same order against native projection. A collapsed continuous visual chain can leave an insertion gap at the side seam with two valid logical destinations. The drag snapshot must preserve logical ownership and disambiguate the seam by a stable documented target policy, not by Home's animated x or size. Keep current Auto path; use compatible Manual fallback until validated. Existing hover mode can temporarily remove the island (`applyHoverMode`); Manual must not silently lose side membership, and the Home-disabled UX is a product gate. Native commands/selection/close/restore remain independent of motion success.

### Persistence and native open: raise this to a pre-cutover blocker

Zen `ZenWindowSync.sys.mjs:on_TabOpen` creates a peer with addTrustedTab and only then assigns the source tab ID; sync flags are ICON/LABEL/MOVE. TabMove delegates only MOVE. Therefore a peer TabOpen can precede stable identity and a local side-only change may emit no native TabMove. `ZenSessionManager.sys.mjs:#collectUsedTabsFromWindows` selects one copy by zenSyncId and active/nonblank priority. A SessionStore custom value written in just one window is not sufficient evidence of durable synced ownership.

Compare (A) native SessionStore side value alone, suitable only if the exact session/sync lifecycle preserves it; (B) native side value plus tightly scoped reconciliation across verified actual native peers using existing lifecycle and identity (no custom data broadcast before peer identity is known); (C) a bounded profile-level side-only metadata index keyed by proven native identity and sync scope. C introduces orphan/closed-tab/restore/ID reuse/private lifecycle and concurrency obligations and is not approved by default. A single-window test cannot choose A. Prefer A/B if proven, otherwise stop and review C explicitly; never combine redundant persistence stores as a hedge. No direct session file or Zen internal sync monkeypatch. Confirm private and unsynced handling before any persistent write.

The native SpaceManager initializes/reuses an empty placeholder, and the mod filters zen-empty-tab out of the projection. A new-tab intent must observe actual eligible creation or proven placeholder conversion, with exact command correlation and restored metadata precedence. A generic 'next TabOpen' flag can be stolen by restore, peer creation, extension or simultaneous open. Do not implement this until actual Gecko/Zen event ordering and return/identity evidence are available; distinguish new/duplicate/restore/adopt/sync. Home/ambiguous-origin fallback, scope of mode setting, special roles and group conflict policy remain open product decisions, not silently chosen in this review.

### Revised gates (same ML0–ML7 IDs)

1. Finish native feasibility (open/restore/adoption, identity and replica persistence) and capture Auto golden structural/geometry fixtures before integration. Pure ML1 experiments can proceed without persistence writes but do not mark ML0 closed or build runtime against an unproven storage adapter.
2. ML1a pure Manual allocation and lossless Auto plan normalization, test-only first. ML1b small existing projection/consumer contract migration with Auto-only runtime, exact equivalence and reentrancy tests. Keep old Auto allocation and current CSS/metrics until an actual consumer needs change; remove superseded paths only after verified cutover.
3. ML2–ML4 metadata/open/drop adapters and failure tests behind an unavailable Manual switch; no partial public mode. ML5 finish real rendering/scroll/hover/CenterMotion/Address/Bunny and keyboard/focus integration. Coordinate fresh HEAD with active Home/drag changes; no broad rewrite to preempt parallel work.
4. ML6 independently challenge partial commits, same-side filtered adjacency, missing/conflicting metadata, two windows, restoration, resize thresholds and stale gestures; verify complexity O(n) per allocation pass (bounded address search multiplier), no new idle polling or persistent mirror cache. ML7 actual Zen/Sine and visual acceptance; no default enable based on source tests.

This review does not certify SessionStore, native event order, performance or runtime behavior. ML0 remains open until native probes/evidence and product decisions resolve the blockers.

## ML0-R2 — adversarial lifecycle and placement review (preview.209, b1bf1ec)

**Status: design review only; ML0 remains OPEN.** Rechecked actual tab-sync, strip-order, window lifecycle, Drag Engine, Split Drop and keyboard paths, plus Zen 1.24.2b Split source. Keep the previous approved product contract and the R/R2 refinements; no runtime change.

### Reduce the contract further

- Do not create four live state machines from the four conceptual layers. Native order remains read-only; side is the only new persistent user datum; the candidate/committed projection is a Layout-owned derived value; motion snapshots stay gesture-local. One published projection reference (or invalid) plus existing owner/token checks is sufficient; no independent revision service for every consumer. An assignment-only change must invalidate the captured projection even if native order, count and rectangles are identical.
- The common plan need only identify visible units, logical ownership and ordered region slots (including controls), with explicit Auto provenance; it must not own native tab operations, store DOM rectangles, replicate selection or implement callbacks. Keep existing node identities. Allocate at most the required fixed region set (upper L/R, lower L/R; Auto combined lower or Manual single-wide lower can reuse a physical region). Reuse the same two plus elements when moving rows; no copies, dynamic lane registry or new per-region RAF loops. Treat a plus as a control, not a native unit in drag/focus/reorder counts.
- Distinguish structural invalidation from cosmetic refresh. TabAttrModified/icon/selection events already call sync; current sync constructs a new order array each pass. Do not treat a new array alone as a changed layout revision or cancel every animation on an icon update. Compare relevant unit/side/region structure and geometry inputs; still retain exact snapshot guard within the current write transaction. Avoid full peer scans, persistence writes or order normalization on resize/hover/frame callbacks. Existing tabFromItem scans entries and nativeSlot scans splitEntries; repeated scans inside a hot consumer can be O(n²) even with O(n) allocation. Measure actual consumers; prefer pass-local lookup from existing entries only where needed, not another persistent mirror index.

### Commands are not just drag

- `tab-view.js.part:createSplitEntry` ArrowLeft/ArrowRight moves a group directly using stripNodes and moveNativeNextTo, bypassing onStripDrop. Keyboard, pointer drop, and any explicit side command must share a small placement validation/translation helper; Drag Engine remains lifecycle-only and keyboard must not manufacture a drag session. Preserve native Ctrl+Tab semantics unless separately approved. Keep visual focus traversal and native MRU distinct; test left row reversal, cross-row movement and empty-side commands.
- **New-tab ordering counterexample:** native order [L2,L1,R1,R2], active L1. If Zen inserts new L3 after L1, setting side=left alone renders [L2,L1,L3,Home], placing it nearest Home rather than replacing the outer plus. Explicit plus must target the exact outer logical insertion gap as well as side. Use at most one native creation; if native order needs correction, use a verified native insertion option or a single permitted relative move and confirm actual filtered order. Do not silently reorder ordinary Ctrl+T/link opens to imitate plus unless approved; existing native insertion semantics and intended side still apply. Distinguish creation succeeded / placement unverified; never delete a created tab, retry creation, or claim full success on an unverified move.
- **Mixed Split:** Zen can create/extend/dissolve groups via native commands outside Nocturne's onSplitDrop; onSplitDrop also may synchronously select the dragged tab and native callbacks can invalidate the source before postcondition. ZenViewSplitter emits ZenSplitViewTabsSplit and ZenTabRemovedFromSplit, including multi-member changes/dissolution. The current tab-sync event list includes removal but not split-created explicitly (other native events/observers may cover it). Verify full native event convergence rather than add a duplicate observer. Use exact full native group membership, not the visible subset or a transient selected pane. Proposal requiring UX approval: a confirmed explicit group-side move assigns the entire group; a newly formed mixed group inherits the known target side when proven; if no trusted target is known, resolve only with stable documented precedence or keep placement unresolved without overwriting restored metadata. On unsplit, retain last confirmed group side for members unless explicit destination overrides it. Never use whichever member is selected now as a persistent conflict resolver. No group-owned second persistence key unless native evidence proves necessary.
- **Native role and filtered adjacency:** opposite-side slots can be ignored for same-side order verification, but native role boundaries cannot. Pinned/Essentials/folder/Glance, hidden members and Workspace changes may constrain valid native anchors. Do not move across a native container just to satisfy a visual gap; classify before mutation, reject unsupported target without changing native data. A visual empty side is not a native empty Workspace; a side-only move must preserve native membership. A whole group cannot be considered confirmed based only on visible members. Keep unsupported-role rendering and eligibility policy open rather than hide tabs.

### Concurrency and recovery

- Existing drag-engine native topology witness checks source/native order, groups, parents, pin and workspace but not Manual ownership. Capture the committed projection identity and invalidate on structural side/mode change from another window; distinguish scroll/hover pose changes from ownership changes. Check the exact captured token again after synchronous native callbacks. Current own-commit bypass uses data-op-drag-commit; do not extend this DOM flag into an authorization for unrelated side writes. Old completion must not overwrite a newer gesture or assignment.
- Native order mutation and multiple SessionStore writes cannot be assumed atomic. For one-window and peer writes preflight exact role/identity, verify outcomes, expose unresolved partial metadata separately from native result, and retain native usability. A display can remain atomic at group granularity even if metadata write is partial; do not pretend disk durability. Do not implement timestamp last-writer-wins, a distributed lock, or generic rollback without demonstrated need.
